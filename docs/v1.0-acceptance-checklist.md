# VibeSorter 1.0 acceptance checklist

This checklist is the release gate, not a claim that every item is already complete. Mark an item complete only when there is evidence from a test, build artifact, reproducible procedure, or reviewed documentation.

## Product correctness

- [ ] Spatial features distinguish the true central region from corners and edges; regression tests cover center-only, corner-only, and edge-only changes.
- [ ] Cache invalidation is verified when feature extraction semantics change.
- [ ] Media-type taxonomy documentation distinguishes automatic predictions from manually supplied values.
- [ ] Human-labeled evaluation data is versioned, privacy/licensing reviewed, and separated into tuning and holdout sets.
- [ ] Release report includes per-vibe support, precision, recall, F1, confusion matrix for dominant labels, and multi-label metrics where applicable.
- [ ] Raw heuristic scores are described as ranking signals, not calibrated probabilities.

## User workflow and data safety

- [ ] Read-only commands are verified not to mutate source images.
- [ ] Applying organization proposals requires explicit confirmation and retains journal/rollback protections.
- [ ] Failure-path tests cover conflicts, partial batches, rollback verification, and missing/unreadable source files.
- [ ] Cache, history, backup, reset, and uninstall behavior is documented.

## Desktop and platform confidence

- [ ] Packaged desktop app opens and displays results for a library path containing spaces and non-ASCII characters.
- [ ] Cancel → restart → cancel is tested.
- [ ] Backend/sidecar startup failure, unexpected exit, and database errors are handled clearly.
- [ ] Windows, macOS, and Linux artifacts are built and smoke-tested on supported runners; limitations of GUI automation are documented.
- [ ] Privacy and network boundaries are documented and verified for the desktop and browser interfaces.

## Installation and release pipeline

- [ ] Python distribution name is confirmed available or a non-conflicting name is selected.
- [ ] Wheel and source distribution build and install in a clean environment.
- [ ] Version values agree across Python package, desktop package, and release metadata.
- [ ] A version tag triggers checks and builds from that exact tagged commit.
- [ ] Required checks must pass before publishing.
- [ ] Release includes platform artifacts, source archive, release notes, SHA-256 checksums, and artifact provenance where supported.
- [ ] Artifact contents and sizes are inspected; unpacked build directories are not accidentally uploaded as distributables.

## Documentation and support

- [ ] Quickstart covers install, first analysis, cache location, search, review, apply, and rollback.
- [ ] Supported image formats, platforms, known limitations, privacy behavior, and troubleshooting are current.
- [ ] Bug-report templates request reproducible steps and relevant logs without encouraging users to upload private image libraries.
- [ ] Release notes distinguish validated improvements from known limitations.

## Final go/no-go

- [ ] Ruff and the full Python test suite pass on all supported Python versions.
- [ ] All release-blocking issues are closed or explicitly deferred in release notes.
- [ ] Required CI passes on the release candidate.
- [ ] At least one clean-install verification is completed for each supported release channel.
- [ ] A release candidate is tagged and its published checksums are verified.
- [ ] Maintainer reviews and approves the final go/no-go decision.
